# 决策记录

每条记录写清楚：什么时候、定了什么、为什么。新的决定追加在最后；推翻旧决定时，新增一条并注明替代了哪条，不要直接改旧记录。

---

### 1. 离线逐帧渲染，替代边播边录（2026-10-15）
- **决定**：
  - 画面由无头 Chromium 按 1/fps 逐帧调用 `renderFrame(ctx, t)` 生成；
  - 声音用 `OfflineAudioContext` 按同一条时间轴合成；
  - 最后用 ffmpeg 合成。
- **理由**：原型用 MediaRecorder 边播边录，导出的视频会卡顿、音画不同步。离线渲染时画面和声音都只依赖时间轴，从源头保证同步。

### 2. Playwright + Chromium + Canvas 2D，锁定 Playwright 1.63.0（2026-10-15）
- **决定**：渲染用 Playwright 驱动无头 Chromium。Playwright 锁定 1.63.0，对应 Chromium 1243。
- **理由**：
  - 原型就是 Canvas 2D 加 Web Audio，在浏览器里渲染能和原型逐像素一致；
  - 本机已缓存 Chromium 1243，不用重新下载；
  - 升级 Chromium 可能改变抗锯齿，所以锁版本。升级后要重跑原型对比。

### 3. 并行渲染页 + 纯度守卫（2026-10-15）
- **决定**：
  - 默认开 6 个渲染页，每页一个独立的浏览器 context，乱序领帧、按序写给 ffmpeg；
  - 渲染期间禁用 `Math.random`、`Date.now`、`performance.now`、`requestAnimationFrame`；
  - 每帧开始时 `ctx.reset()`，timeline 深冻结。
- **理由**：
  - 并行渲染提速约 3 倍；
  - 乱序渲染本身就能检验 renderFrame 有没有偷偷保留状态，纯度守卫则把不确定的写法变成立刻报错。

### 4. 帧用 PNG 管道直接交给 ffmpeg，不落盘（2026-10-15）
- **理由**：1080×1920 的渐变画面单帧 PNG 有 1～3 MB，一期几千帧会占好几 GB 硬盘。

### 5. 输出规格（2026-10-15）
- **决定**：
  - 视频：H.264 High、crf 18、yuv420p、BT.709 标记、GOP 2 秒；
  - 音频：AAC 192k、48kHz 立体声；
  - `+faststart`；
  - 默认 1080×1920 @30fps；草稿 540×960 @15fps（草稿规格是用户指定的）。
- **理由**：抖音、小红书、Reels、Shorts、B 站、YouTube 都能直接接受这组参数。

### 6. 目录分层：core / plugins / episodes / cli（2026-10-15）
- **决定**：
  - 流水线必需的放 `core/`；
  - 可选的复用组件放 `plugins/`（用户最初提议叫 `tools/`）；
  - 单期专属代码放 `episodes/`；
  - Node 命令入口放 `cli/`。
- **理由**：
  - "plugins" 直接表达"按统一接口注册、按需选用"，每个插件导出 `meta`，可以自动列出清单；
  - `cli/` 单独放，是为了把只在 Node 里跑的代码和浏览器端代码分开。
- **依赖方向**：episodes → plugins → core，core 不反向引用。

### 7. 字体缓存（2026-10-15）
- **决定**：渲染器把 Google Fonts 的请求缓存到 `.cache/http/`。episode 必须在 `fonts.text` 里列出所有会画的字；中途触发字体加载会重画该帧并记警告。
- **理由**：字形没加载完就截帧，会出现回退字体，各并行页之间也会不一致。

### 8. 第一期的迁移方式（2026-10-15）
- **决定**：
  - 原样保留原型的视觉参数和音色参数，与原型逐像素一致；
  - 混响噪声改用固定种子；
  - 去掉原型里的编辑界面（加句子、勾选、单句试听），句子改成 `sentences.js` 数据文件；
  - 封面用原型的静止海报画面。
- **理由**：验收要求"画面与原型一致"；随机混响会让每次渲染的声音不同；编辑界面的功能由预览页和数据文件代替。

### 9. 第一期的两处跳变不修（2026-10-15）
- **决定**：53 秒和 44 秒的花朝向跳变都保持原样。
- **理由**：都是原型就有的。用户看过后决定第一期不再改动。

### 10. GitHub 公开仓库，直接提交到 main（2026-10-15）
- **决定**：仓库为 github.com/Boshugege/video-gen，公开（用户选择）。目前单人开发，直接提交到 `main` 并推送。

### 11. 素材加载的设计（2026-10-15）
- **决定**：
  - 素材在 `setup()` 之前全部加载、解码完；
  - 音频统一按混音采样率（48kHz）解码；
  - 不支持网络地址；
  - 每个素材的 sha256 记进 render.json，可选在声明里写 sha256 做校验。
- **理由**：
  - setup 能读到配音时长，用它排场景；
  - 渲染器和预览页拿到的是同一份解码数据；
  - 不依赖网络才能离线复现；
  - 有了 sha256，事后能确认一条成片用的是哪版素材。
- **已验证**：mp3 和 m4a 的编码器延迟在解码时被正确去除，wav、mp3、m4a 三种格式的同步误差都只有 0.06 ms。

### 12. 音频素材不进 git（2026-10-15）
- **决定**：
  - 所有音频和视频文件都不进 git，只留在本地 `episodes/<id>/assets/`；
  - 每期 `notes.md` 记录素材来源和授权，`npm run assets` 检查是否齐全；
  - 图片可以提交（受 5MB 钩子限制）；
  - 例外：`_asset-test` 的合成测试素材已提交。
- **理由**：仓库公开，背景音乐和配音可能有版权限制，体积也大。
- **备注**：这是 Claude 定的默认值，已告知用户，用户可以要求改成别的方案（例如私有存储）。

### 13. 一条命令跑完回归（2026-10-15）
- **决定**：`npm run regress` 依次跑单元测试、音画同步测试、素材同步测试、第一期与原型对比。改了 core、plugins、presets 后必须跑，全部通过才提交。
- **理由**：仓库会在不同会话里接力开发，需要一个不依赖记忆的"有没有改坏"的判断标准。

### 14. 第二期：每 3 帧一句、540 句、全片卡 60 秒、不做网页（2026-10-16）
- **决定**：
  - 创意原案是每 2 帧一句、900 句。改成每 3 帧一句（用户选择）；
  - 全片卡死 60 秒（用户选择；另一个选项是 600 句、约 66 秒）。片段流 54 秒 = 540 句，6–8 秒的定格示范和最后 4 秒的网格不走片段流；
  - 不做观众提交句子的拼图网页，只用评论区（用户选择）。
- **理由**：2 帧一句经平台二次压缩后，单帧可能读不清；创意自己的小贴士也建议读不清就改 3 帧。

### 15. 第二期的故事全文照常提交到公开仓库（2026-10-16）
- **决定**：540 句正文（含结局）在 `episodes/2026-W43-pause-to-read/story.js`，照常提交（用户选择）。
- **备注**：另一个选项是只留本地、仓库里放占位故事，等观众拼完再提交。用户接受任何人都能在 GitHub 上读到全文和结局。

### 16. 第二期的片段只画在画面上，不进 SRT（2026-10-16）
- **决定**：SRT 只有 7 句旁白，540 句片段不进字幕。
- **理由**：上传 SRT 就等于公开完整剧本，"暂停才读得到"的玩法就没了。

### 17. 第二期的画面为压缩让路（2026-10-16）
- **决定**：
  - 背景纯黑，不加原案里"满屏闪烁的噪点字"，每帧只有一句字在变；
  - 原案"门内字号变小"改为字号不变，只让光变亮；
  - 片段文字先用背景色描一圈粗边再填色，不用模糊阴影。这样门板边线和光从字后面经过时，碰不到笔画。
- **理由**：平台二次压缩时，满屏高频变化的细节会抢码率，真正要读的字就会变糊。实测按 540p 0.8 Mbps 重编码后，随机抽 12 帧都能读清。

### 18. 中文折行：标点优先，再按浏览器分词（2026-10-16）
- **决定**：片段中文最多两行：
  - 能断在标点后就断在标点后；
  - 否则用 `Intl.Segmenter('zh')` 找最均衡的词边界，短引语不拆；
  - 实在不行才逐字断。
  
  另有 12 句断不好，改了措辞。
- **理由**：逐字折行时，有近百句断在词中间（"门 / 缝""收音 / 机"）。观众要截图发评论，断得难看会直接影响玩法。
- **代价**：断行依赖 Chromium 的 ICU 词典，升级 Playwright 后要重看排版。这套逻辑先放在这一期里，下一期还要用时再提到 `plugins/text`。

### 19. 片段流按整数帧计时（2026-10-16）
- **决定**：
  - 当前句 = floor(片段流帧号 / 3)，帧号用 `Math.round(t × 30)` 换算；
  - 时间规则集中在 `stream.js`，setup 排的咔哒事件和 renderFrame 取句都从这里算。
- **理由**：
  - 用浮点秒数相除，会在换句的边界处差一帧；
  - 草稿是 15fps，按整数帧算，草稿里每一帧显示的句子和成片同一时刻一致。
- **已验证**：混音里 540 次起音，相邻间隔全部是 100.00 ms。
